## 1. 功能一：动态餐盘设计（第一优先级）

### 1.1 用户目标

用户从真实食材库挑选食品，指定克重，实时看到整餐的营养摘要随食材和克重变化。这是三个功能的前置依赖。

### 1.2 数据与单位

- 每 100 克基准：`summary_per_100g`（能量/蛋白/脂肪/碳水/纤维/糖/钠）+ 完整 `nutrients[]`
- 份量参考：`portions[].gram_weight`（质量单位，非品牌商品）
- 质量：`quality_flag` / `is_available` / `missing_count`
- 能量：单一值（后端已按 1008 → 2048 → 2047 取一个），kJ 不并入 kcal

### 1.3 前端计算契约

```
某营养合计 = Σ（某食材某营养每 100g 值 × 克重 / 100）
仅累加 quality_flag == "ok" 且 amount != null 的项
未知项不按 0 处理，单独返回：
  - covered_count（已知克数上的已知项计数）
  - covered_grams（已知克重合计）
  - known_ratio = covered_grams / total_plate_grams（整餐已知克重覆盖率）
```

### 1.4 用户流程

1. 用户在食材库搜索 → 点击「加入餐盘」。
2. 弹出选择器，默认显示份量列表中第一个可用的克重（若无则默认 100g，注明"无份量参考"），支持手动输入克重（g）。
3. 食材进入餐盘区，显示插画、中文名、英文名、克重、核心营养摘要。
4. 克重可随时调（步进 1g），右侧营养面板实时更新。
5. 支持删除、清空、最多上限（沿用当前 8 种，可调整）。

### 1.5 关键交互

- 点击餐盘食材 → 右侧营养面板高亮该行贡献。
- 拖拽顺序（非必需，本阶段可省略）。
- 加入新食材时自动推荐克重（从 `portions` 取第一个 `quality_flag='ok'` 的 `gram_weight`，单位为 g；若份量质量非 ok 则提示"份量质量存疑"）。
- 核心营养条目旁边显示 "？" 悬浮说明缺失处理规则。

### 1.6 界面调整

- 餐盘卡片新增克重输入框 + "选择份量"按钮。
- 右侧营养面板从占位改为四个核心营养 tile，合计值实时刷新。
- 详情抽屉的"份量"小节可直接点击"以此份量加入餐盘"。

### 1.7 图表选择理由

本阶段没有新图表；右侧用数字 tile 即可，因为"实时刷新"比"视觉形式"更重要。真正需要贡献对比时由功能二承担。

### 1.8 复用的现有组件

- `FoodCard` 保留，餐盘区用更紧凑的内嵌卡片。
- `FoodDetailDrawer` 的份量小节加一个按钮。
- `format.ts`、`types.ts`、`queries.ts` 继续使用。
- 新增：`lib/calculator.ts`（本地纯函数，无副作用）、`features/designer/Plate.tsx`、`features/designer/NutritionPanel.tsx`。

### 1.9 验收标准

- [ ] 加入任一 Foundation/SR Legacy 食品，选择份量或手动克重，核心营养合计与用 Excel 手算（每 100g 值 × 克重 / 100）一致。
- [ ] 加入含能量缺失的食品时，能量合计旁边显示"部分未知（X 种食材缺少能量数据）"，不按 0 处理。
- [ ] 加入份量质量非 ok 的食品时，推荐克重的标签上出现质量事件说明。
- [ ] 克重调整 1g 后，合计值在 100ms 内刷新（本地计算，不请求后端）。
- [ ] 浏览器 DevTools 无 API 调用（计算完全前端本地）。
- [ ] `npm run typecheck`、`npm run build`、`npm run lint` 通过。
- [ ] 至少 10 条真实食品手动核算通过，记录在 `data/build/validation_report.md` 的黄金样本小节。

### 1.10 测试

- 手工计算 vs 前端计算的单元测试（Vitest 或手写脚本，后续决定是否添加测试运行器）。
- 前端 E2E：加入 → 改克重 → 删除 → 合计刷新。

## 2. 功能二：营养来源透视（第二优先级）

### 2.1 用户目标

用户选择一项营养指标，看到餐盘中每种食材的实际贡献与相对占比，并能点击图表反向高亮餐盘食材。

### 2.2 数据与单位

功能一已经计算好的"每食材某营养贡献 = 每 100g 值 × 克重 / 100"，复用功能一的合计，不重复请求后端。

### 2.3 用户流程

1. 右侧营养面板切换到"贡献"视图。
2. 从核心营养下拉选择（能量、蛋白、脂肪、碳水、纤维、钠）。
3. 看到一张贡献条形图，X 轴是克重贡献，Y 轴是食材列表。
4. 条形图上方显示合计值与百分比，最右侧是缺失提示（若有）。
5. 点击某条 → 餐盘对应食材高亮（边框、背景色变化）。
6. 高亮可通过 Esc 或再次点击取消。

### 2.4 图表选择理由：水平贡献条形图

- **为什么不是桑基图**：餐盘食材固定（功能一已经锁定），不是流向结构；条形图更直观，用户能立刻比较"谁最多谁最少"。桑基图在结构表达上不如条形图清晰，且对数据完整性要求更高。
- **为什么不是饼图**：饼图在类别超过 5 个时标签挤压，且用户需要精确数字。
- **条形图的交互天然适合反向高亮**：点击条目就是选中对应食材，无需再做映射。

### 2.5 关键交互

- 鼠标悬停条形图 → tooltip 显示：食材名、英文原名、克重贡献、相对占比（%）、每 100g 值。
- 条形图按贡献降序排列，缺失食材单独放在"未知"分组并注明原因。
- 百分比显示到 1 位小数，总和非 100% 时自动补齐并标注"数据存在缺失项"。

### 2.6 复用的现有组件

- `ChartShell` 复用（ECharts 核心 + Tooltip）。
- 图标、卡片、中文文案直接复用。
- 新增：`features/designer/ContributionChart.tsx`、`features/designer/NutrientPicker.tsx`。

### 2.7 验收标准

- [ ] 选择任一核心营养，条形图合计 = 该营养餐盘合计（由功能一计算）。
- [ ] 点击条形图某条 → 餐盘对应食材立即高亮；Esc 可取消。
- [ ] 贡献值缺失的食材不出现在条形图中，图表下方单独列出"缺失：X 种食材缺少此营养"。
- [ ] 图表可在 100ms 内响应克重变化（依赖功能一）。
- [ ] `npm run typecheck`、`npm run build`、`npm run lint` 通过。

### 2.8 测试

- 条形图贡献合计 = 餐盘合计的算术一致性。
- 点击图表高亮正确食材（视觉+可访问性检查）。

## 3. 功能三：餐盘差异与食材替换模拟（第三优先级）

### 3.1 用户目标

用户保存两套餐盘 A 与 B，并排比较核心营养差异，追踪差异来自哪些食材；替换操作先预览再确认。

### 3.2 数据与单位

复用功能一的餐盘 + 克重 + 本地计算；方案保存在 IndexedDB（浏览器本地，符合项目规则"方案与偏好只存浏览器"）。替换预览调用功能二的贡献计算看"哪种食材/份量改动导致差异"。

### 3.3 用户流程

**保存方案 → 比较 → 替换 → 确认应用**：

1. 在餐盘设计器点击"保存方案" → IndexedDB 存储餐盘（食材 + 克重 + dataVersion）+ 营养快照。
2. 打开"方案对比"页 → 选择方案 A、方案 B → 或复制当前餐盘作为 A/B。
3. 并排显示两套餐盘（食材卡片 + 克重 + 营养摘要 tile）。
4. 核心营养 tile 用 Δ 差值突出主要变化（绝对值超 10% 才高亮），点击 tile 切换到"贡献差异视图"——两盘各食材贡献条形图，颜色不同，差值大的食材自动排到顶部。
5. 在 A 盘点击"替换" → 弹出替换面板：从食材库搜索候选（同类食材优先），预览替换后的营养合计与 Δ，点击"应用"才真正改动，不点击则关闭面板保持原状。
6. 支持"撤销替换"（最近一次，简单历史栈）。

### 3.4 图表选择理由：并排贡献条形图 + Δ 高亮

- **并排条形图**（双 Y 轴，颜色区分 A/B）：直观比较同一种营养在两盘中的贡献分布。关键是**重叠区间**——如果替换只是换一种食材，条形图让用户一眼看出"哪些食材上发生了变化"。
- **Δ 差值条形图**（仅正/负方向）：替代热力图/桑基图，在"突出主要差异"上比热力图清晰，且交互与功能二一致，复用 ChartShell 不引入新依赖。

### 3.5 关键交互

- 保存方案时记录 `dataVersion`，版本变化时在"我的方案"页弹出提示（按项目规则）。
- 替换搜索默认按分类匹配（功能四的分类）。
- Δ 超过 10% 的营养 tile 自动加橙色边框 + 箭头（↑↓）。
- 替换预览面板实时刷新，不阻塞输入。

### 3.6 复用的现有组件

- `AppShell` 的路由、`FoodBrowser` 的搜索/分类筛选、`ChartShell`、`Badge`、`FoodIcon` 全部复用。
- 新增：`features/plans/PlanStorage.ts`（IndexedDB 封装）、`features/plans/ComparePanel.tsx`、`features/plans/ReplacePreview.tsx`、更新 `ComparePage.tsx` 与 `PlansPage.tsx`。

### 3.7 验收标准

- [ ] 保存 → 刷新浏览器 → 方案恢复；dataVersion 字段写入。
- [ ] 方案 A/B 并排显示，核心营养 Δ 正确。
- [ ] 替换预览 → 应用 → 撤销完整链路走通，每次替换后营养合计刷新。
- [ ] IndexedDB 写入不请求后端，离线可用。
- [ ] 至少 2 套保存的方案对比手动核算差异正确。
- [ ] `npm run typecheck`、`npm run build`、`npm run lint` 通过。

### 3.8 测试

- IndexedDB 读写 + dataVersion 变更检测。
- Δ 算术一致性。
- 替换预览 → 应用 → 撤销流程。

## 4. 功能四：食材营养探索地图（第四优先级）

### 4.1 用户目标

在真实每 100g 营养空间中探索不同食品的分布，理解"什么样的食品属于什么营养区间"，并能从探索直接把食材加入餐盘。

### 4.2 数据与单位

- 每 100g 基准，核心营养完整列表。
- 全量 `foods` 列表（分页/滚动），不再强制前 40 条样本。
- 点颜色按分类（grain/protein/dairy/vegetable/fruit/fat/beverage/snack/other）。
- 点形状可扩展（数据类型：Foundation 圆、SR 方、FNDDS 三角），但第一版只按颜色区分。

### 4.3 当前问题与调整

当前散点图用 `page_size=40` + `page=1` + `sort=alpha_zh`，不是全量。调整为：

- 默认范围仍可聚焦 Foundation（规模合适，分布清晰），但**明确让用户切到其他数据集或全量**。
- 切换"全量"时用滚动或虚拟列表处理大数据点（sample 库 1,285 点可直接渲染；正式库 Foundation+SR+FNDDS 合计约 13,600 点时考虑采样或聚合）。
- 点颜色固定按分类；悬停显示中文名 + 英文名 + FDC ID + 核心营养；点击点 → 打开详情抽屉，抽屉加"加入餐盘"按钮。
- 搜索框支持"在散点图上高亮匹配点"（半透明蒙版 + 匹配点放大）。

### 4.4 图表选择理由：蛋白质-脂肪散点图（第一版固定）

- 蛋白质 vs 脂肪是用户最熟悉的营养维度，且 Foundation/SR Legacy 数据最完整。
- 第一版固定这一对维度，后续可扩展下拉切换（如碳水 vs 纤维、能量 vs 钠）。
- **不**做热力矩阵/桑基图/流向图，第一版只保留一对维度的散点图，足够解决"探索→加入餐盘"的闭环。

### 4.5 用户流程

1. 进入营养探索 → 默认 Foundation 数据集散点图。
2. 数据集下拉切换 Foundation/SR Legacy/FNDDS/全部；切换后图表重新渲染。
3. 悬停点 → tooltip；点击点 → 详情抽屉（带"加入餐盘"）。
4. 搜索框输入 → 匹配点高亮放大，非匹配点半透明。
5. 图例点击切换分类可见性（ECharts 原生支持）。

### 4.6 关键交互

- "加入餐盘"按钮复用功能一的选择器（份量/克重）。
- 详情抽屉与餐盘设计器共用同一个组件，不重画。
- 图表右上角加"关键点标注"按钮 → 切换显示/隐藏按贡献排序的前 N 个点的中文标签（ECharts 原生 `scatter` + `label` 即可）。

## 5. 暂缓功能与理由

| 功能 | 暂缓理由 |
| --- | --- |
| 营养时间回放 | 第一版没有餐盘保存历史，"回放"没有数据源；等方案保存（功能三）后再评估。 |
| 组合优化挑战器 | 本质是"算法自动生成餐盘"，复杂度高，且用户目标是"设计→理解→调整"而非"让 AI 给答案"；放到第二版。 |
| 多方案决策沙盘 | 是功能三的扩展（方案 A/B/C 多维对比）；先把两方案的核心差异做扎实。 |
| 营养指纹 | 是"餐盘归一化营养画像"的概念化输出；第一版条形图 + Δ 已足够表达，指纹是锦上添花。 |
| 独立桑基图 | 已在功能二/三的理由中说明：条形图更直观，结构表达并非本阶段瓶颈。 |
| 复杂报告生成器 | 第一版没有任何可导出的数据结构（PDF/图片）；等方案保存（功能三）后再做。 |
| 拖拽自由摆盘 | 餐盘克重+计算（功能一）未落地之前，拖拽只是视觉玩具；落地后再补。 |
| 品牌库默认进入搜索 | 品牌商品分类编码为空，份量不可靠；等独立品牌体验（阶段 7）再做。 |

## 6. 实施顺序（增量、可验收、可停）

| 阶段 | 交付物 | 依赖 | 验证方式 |
| --- | --- | --- | --- |
| **阶段 2a（功能一：克重 + 计算）** | 餐盘加克重输入、份量选择器、右侧营养 tile 实时刷新、本地计算器 | 无 | 10 条黄金样本手算对照 |
| **阶段 2b（功能二：贡献条形图）** | 右侧"贡献"视图、点击图表高亮餐盘食材 | 2a | 贡献合计 = 餐盘合计；点击匹配高亮 |
| **阶段 2c（功能三：保存 + 对比 + 替换）** | IndexedDB 方案存储、并排对比页、替换预览面板 | 2a、2b | 保存→刷新→恢复；替换→应用→撤销 |
| **阶段 2d（功能四：全量探索地图）** | 散点图全量数据集、维度切换、点高亮搜索、详情抽屉联动 | 2a（加入餐盘联动） | Foundation/SR/FNDDS 点渲染 + 详情抽屉加入 |

### 为什么这个顺序

1. 功能二、三都依赖"克重 + 计算"，先做功能一才能解锁后续一切。
2. 功能二对"理解营养来源"是直接闭环，比"保存方案"更能体现产品价值。
3. 功能四的探索地图现在已有骨架，补齐全量和交互是低风险增量，放在最后做锦上添花。
4. 每个阶段**都有独立验收标准**，可随时停；不做"功能 N 做完才能开始功能 N+1"的长链路依赖。

### 每一阶段的退出门槛

- 真实数据、真实计算、真实交互；不允许用 mock/占位图/0 填充让页面"看起来完整"。
- `npm run typecheck`、`npm run build`、`npm run lint` 全部通过。
- 至少一次浏览器联调（打开对应页面，走完整主路径）。
- 黄金样本记录在 `data/build/validation_report.md`，不得跳过。
- 如果中途发现 API 缺字段，必须**在前端本地解决或提出最小后端增量**（当前没有这种需求）；禁止重写 ETL、禁止重写后端框架。

## 9. 风险与边界

- **样本库 1,285 食品**：当前是 sample 库，正式全量（约 13,600 默认库食品 + 1,999,950 品牌商品）下前端散点图的渲染性能、搜索响应、缓存策略都需要重新评估。第一版以 sample 库验证逻辑，全量优化放到阶段 7。
- **品牌库份量不可靠**：品牌商品没有 `food_portion.csv`，UI 必须避免伪造家庭份量克重；"按份量加入"对品牌商品应禁用或只展示标签份量。
- **缺失值≠0** 是硬性规则：任何合计、贡献、差异都不能突破；如果某营养在整餐中所有食材都缺失，合计显示 `—` 并标注"全部未知"。
- **中文词典译名不准确**：当前 sample 库中约 621 条为 glossary 译名，显示时必须突出英文原名并标注"词典译名（待核验）"，不能让用户误把候选翻译当作事实。
- **能量优先级** 已在后端实现，前端不能重复这个逻辑；前端只调用后端返回的单一能量值。
